# 教培CRM部门协同改造 产品需求文档

V1.0  ·  2026年10月25日  ·  业务评审与产品开发依据

活动课专项更新：2026年10月26日的[活动课专项PRD优化开发文档](./活动课专项PRD优化开发文档.md)补充了多课节、拼团、教室名额、运营手动推送及按班级跟进规则；活动课相关内容冲突时，以专项文档的最新确认规则为准。

本次改造围绕运营获客、校区转化、教学续报和教务服务建立连续的业务流程。系统应让每条业务有明确主责人，每位员工只操作授权范围内的数据，并以费用缴清作为成交与续报成功的判断依据。

## 1 业务边界与已确认规则

| 编号 | 已确认规则 |
| --- | --- |
| C01 | 运营负责获客和活动、体验课报名；校区招生承接并转化正价课。运营可查看下游结果，不承担正价沟通转化。 |
| C02 | 活动承接校区由学生选择的活动课程参加校区确定。 |
| C03 | 教学部承担活动课和正价课授课。授课老师主责续报，教务参与服务与续报协同。 |
| C04 | 教务按班级分配，可以负责多名老师的班级；绩效关联其全部负责学生的续报表现。 |
| C05 | 续报期由教学部人工规定，一般同一年级一致。 |
| C06 | 所有应缴费用交清才计成功；定金、部分付款不算成交或续报成功。 |

此前按学部、年级和招生组划分权限的方案已撤回。本版以部门职责、校区范围、班级关系和具体任务归属为基础；年级用于课程与续报期配置。

## 2 核心改造优先级

P0：员工授权与数据隔离、活动交接、正价转化、收款状态、班级分工、续报主责、员工交接及审计。先保证流程可执行、权责清楚、成功口径一致。

P1：转介绍与拓科、指标明细与归因、原营销入口接入、异常提醒与批量处理。财务核销、退费与真实账号鉴权属于正式上线前必备能力。

除上表外，本文的流程细节与技术约束为产品建议。第9部分集中列出仍需业务决策的规则，避免把演示默认值当成已确认制度。

## 3 获客到正价转化流程

### R01 活动报名和校区选择 P0

运营创建活动或体验课程，配置可参加校区、费用及授课安排。登记时选择学生、活动与参加校区，保留获客渠道、来源活动和登记员工。提交后学生选择的校区成为接收校区，不按录入人的所属部门或学生年级自动覆盖。

报名、收款、到课、交接分别保存状态。同一学生可以参加不同活动；同一活动重复提交应提示已有报名。手机号只用于查重提示，不能把共用家长手机号的兄弟姐妹自动合并。

### R02 校区接收与分配 P0

运营在活动报名列表多选或全选后，主动点击“推送校区”，记录才进入各自所选校区的待承接队列；未缴清、未成团也允许推送，家长提交报名本身不触发自动推送。校区主管按对应班级查看并指定本校区顾问；同一孩子再次报名同校区活动课时优先推荐原顾问，仍由主管确认或调整。批量推送与分配须防止重复处理并保存交接记录。

运营保留来源关系及下游结果查看权；顾问获得该任务的跟进权。运营可查看承接人、当前阶段、是否缴清及成功时间。招生沟通详情、完整付款凭证默认不因来源关系而开放。

### R03 顾问转化与异常处理 P0

顾问跟进本人任务，可记录沟通、创建正价报名订单。校区自拓线索进入同一转化流程，来源标记为校区自拓。主管可改派本校区任务，跨校区交接必须记录学生意愿、接收校区、责任人和原因。

| 对象 | 主要状态 | 状态变化依据 |
| --- | --- | --- |
| 活动交接 | 未提交 → 待接收 → 已接收；待接收 → 已退回 → 待接收 | 运营提交；目标校区主管接收或退回。 |
| 转化任务 | 待跟进 → 跟进中 → 待缴清 → 已成功；可关闭为未成交 | 顾问跟进和建单；费用缴清自动成功；关闭需原因。 |
| 订单收款 | 未付款 → 部分付款 → 已缴清 | 由有效收款记录计算，不能手工修改成功标签。 |
| 活动到课 | 未到课 → 已到课 / 未出席 | 由授课或活动执行人员记录；不改变收款状态。 |

建议：学生取消活动或更换校区时，保留原报名及变更轨迹；存在订单、授课或服务记录时不得直接删除。活动费未缴清能否交接、取消后如何处理承接任务，见D01。

## 4 员工权限与分配规则

R04 权限采用“岗位动作＋该岗位的数据范围＋业务责任关系”组合授权。部门表示组织归属；校区表示经营范围；班级与任务决定具体可操作对象。员工兼岗时，每项岗位单独绑定范围。以下为建议权限矩阵。

| 岗位 | 默认数据范围 | 允许的核心动作 | 限制 |
| --- | --- | --- | --- |
| 运营专员 | 本人登记的活动和来源记录 | 登记、提交校区、查转化结果 | 不操作正价转化或续报 |
| 运营主管 | 所辖运营团队来源记录 | 管理活动、调整分工、看团队结果 | 不自动取得招生跟进权 |
| 招生顾问 | 分配给本人的转化任务 | 跟进、建正价订单、关闭未成交 | 不操作其他顾问或校区任务 |
| 校区招生主管 | 明确授权的校区 | 接收、退回、分配、改派、看校区报表 | 跨校区须单独授权 |
| 授课老师 | 本人授课班级及对应课程记录 | 授课记录、续报主责、登记转介绍 | 不管理其他老师班级 |
| 教学主管 | 明确授权的教学管理范围 | 配置续报期、教师安排、教学汇总 | 不默认拥有收款或财务修改权 |
| 教务 | 本人服务班级及对应课程记录 | 沟通服务、续报协同、拓科、转介绍 | 不默认查看学生其他班级记录 |
| 教务主管 | 明确授权的教务管理范围 | 分配服务班级、处理交接、看汇总 | 不改授课主责和历史成交归属 |
| 财务 | 授权校区内订单与收款 | 核销收款、对账；按授权处理退费 | 不修改来源或招生跟进 |
| 管理员 | 系统配置与授权管理范围 | 配置组织、员工授权、交接、审计 | 敏感财务操作仍需独立授权 |

### 权限分配界面

新增员工时依次设置组织部门、岗位及校区范围；老师绑定授课班级，教务绑定服务班级，顾问通过任务分配获得线索。保存前展示“可看哪些数据、可做哪些动作”的授权摘要。

兼岗示例：A校区招生主管＋B校区教师，只能管理A校区招生、查看B校区本人授课班级，不能组合出B校区招生主管权限。

### 字段和操作边界

查看手机号、查看订单金额、导出、批量改派、收款、退费分别授权。列表、搜索、详情、统计和导出统一校验范围；直接访问记录也必须校验。界面隐藏按钮不能代替服务端鉴权。

## 5 班级服务和续报协作

### R05 班级绑定教师与教务 P0

班级保存校区、年级、科目、学期、业务类型、授课老师和服务教务。学生通过班级报名关系进入老师与教务的工作范围。一个教务可覆盖多名老师的班级，工作台按其负责班级汇总学生与待办。

建议先按每班一名主责老师、一名主责教务建模，另留协同成员能力。换班、换教师或换教务时保存生效日期及历史关系；同一学生在不同班级的课程、服务和续报记录分别授权，基础档案仅展示必要信息。

### R06 续报期与责任分工 P0

教学主管按年级配置续报期，明确开始日期、结束日期、原学期、目标学期和适用范围。同一年级默认共用一套规则；如需校区例外，需显式配置并展示优先级，不能出现多条规则同时命中。

授课老师是续报任务主责人，教务按所服务班级协同沟通。任务显示主责老师、协同教务、原课程、目标课程、跟进记录及缴费进度，避免同一续报由两个部门各建一笔成交。

续报成功由目标续报订单缴清触发。教学主管可查看年级和教师表现，教务主管可查看教务所负责班级表现。续报期外是否允许新建、补办或继续收款，以及逾期缴清归入哪一期，须按D02确定。

### R07 续报绩效口径 P0

已确认：老师主责续报；教务绩效覆盖本人全部负责学生。建议采用“学生＋科目＋续报期”作为统计单元，同一单元多次跟进或重复下单只算一次；该去重方式仍需业务确认。

| 示例角色 | 应续统计单元 | 已缴清续报 | 续报率 |
| --- | --- | --- | --- |
| 张老师 | 20 | 18 | 90% |
| 李老师 | 30 | 24 | 80% |
| 服务以上两班的王教务 | 50 | 42 | 84% |

示例假设两班统计单元不重叠。教务续报率为42÷50＝84%，不能直接平均两个老师的百分比。若同一学生在多个班级重复出现，应先按确认后的统计单元去重。

同一笔续报可出现在教师主责和教务协同报表中；机构成交按订单或统计单元去重，不能把两份岗位业绩相加。建议续报期开始时保存应续名单，名单变更和责任人变更留痕，以免调班后历史绩效漂移。

## 6 订单收款与指标计算

### R08 统一费用缴清判定 P0

应缴金额、有效已收金额、剩余应缴金额是成功判定的唯一计算来源。对正价与续报订单，应缴金额在合法优惠后确定，所有必缴项目均覆盖；有效收款合计达到应缴金额且无未结清必缴项目，方可进入成功状态。

例如正价应缴3,000元，支付500元后仍为待缴清；再支付2,500元才生成成功时间及统计记录。重复提交同一收款凭证不得重复入账；已缴清订单不得因刷新或再次保存重复计绩效。

建议由财务确认有效收款，保留凭证、时间、操作人。禁止超额收款；误录需要冲正记录，不能覆盖原记录。减免、补差价、零元正价订单及多项目订单分摊须有独立规则；不能仅把应缴金额改为零来完成业绩。

### R09 指标需能追溯到明细 P0和P1

| 指标 | 建议口径 | 必要边界 |
| --- | --- | --- |
| 运营报名人数 | 所负责来源中有效活动报名学生数 | 人数与人次分开；付费及免费有效标准见D01。 |
| 校区正价转化人数 | 范围内正价订单缴清学生数 | 按学生去重；按缴清时间统计；课程维度另列。 |
| 校区正价转化率 | 缴清正价人数 ÷ 有效承接及自拓人数 | 必须同一来源人群与观察周期；分母见D03。 |
| 教师与教务续报率 | 已缴清续报单元 ÷ 应续单元 | 同一期、同一统计粒度；教务汇总后再计算。 |
| 转介绍与拓科 | 推荐来源、任务量、缴清结果及金额 | 机构只计一次成交；比例指标见D04。 |

报表必须显示时间范围、所属校区、统计单位与口径说明，并可下钻明细。收款发生额、成交订单数、成交人数分别展示。部门协同贡献与机构成交汇总使用不同视图。

### R10 退费及历史归属 P0上线要求

当前Demo采用累计缴清口径，后续退款不倒扣历史成功。正式产品应同时保留首次缴清事实和退费事实；净成交、退费率及绩效扣回方式在D04确认后实现，不能用一个“已成功”标签掩盖退款。

建议保存成功时的来源员工、转化顾问、授课老师、服务教务和校区快照。员工改名或调岗不改历史记录；期内交接后的绩效分配规则另行确定。

## 7 系统结构与页面优化

### R11 统一档案与业务关系 P0

| 对象 | 核心关系与字段 | 改造目的 |
| --- | --- | --- |
| 学生档案 | 学生ID、监护人、联系方式；关联多个报名和班级 | 同一学生连续服务，避免重复建档和误合并。 |
| 活动与报名 | 活动ID、学生ID、参加校区、来源、收款及到课 | 把活动获客与后续正价转化串联。 |
| 交接与转化任务 | 原报名、目标校区、主责人、状态、交接历史 | 来源保留，主责可迁移。 |
| 订单与收款 | 业务类型、关联任务、应缴、收款流水、缴清时间 | 统一成功口径，支持退款和对账。 |
| 班级与学生关系 | 教师、教务、课程学期、入班与退出生效时间 | 控制老师与教务的数据范围。 |
| 续报期与续报任务 | 适用年级、原与目标学期、名单、主责与协同 | 明确谁应续、谁负责、何时计成功。 |
| 岗位授权与审计 | 员工ID、岗位及范围、生效时间、变更前后值 | 限制越权，追溯交接和操作。 |

### R12 页面按工作职责组织 P0

工作台展示本人待接收、待跟进、待缴清、续报和服务待办。运营进入活动与获客；校区进入承接与转化；老师进入班级与续报；教务进入服务班级、协同续报、拓科及转介绍；财务进入收款与对账。

员工详情增加岗位范围、授课班级、服务班级及待交接事项。学生详情按活动、课程、订单和服务记录分区授权。无权限时给出明确提示，不以空白列表造成“数据丢失”的误解。

### R13 员工交接与离岗 P0

调岗、缩小范围或停用前检查未完成任务、活动和负责班级。交接清单选择符合岗位及校区条件的接手人，统一提交后再回收旧权限；失败时不允许只改一半。历史来源、成交归属和操作日志保留。

### R14 转介绍与拓科及原有入口 P1

老师、教务可从有权服务的学生登记转介绍，关联推荐人并交目标校区转化；教务可为现有学生建立其他科目的拓科任务。原有课程需求的续报与新增科目分开标记，同一订单不能重复归为正价、续报和拓科成交。

公众号表单、直播获客、商城等旧入口后续统一接入来源、活动报名和交接流程。页面迁移逐项登记入口、对象和权限映射，避免旧入口绕过新规则。

## 8 验收场景与通过标准

以下场景作为核心验收基线。原型可通过员工切换验证交互；正式环境必须同时验证接口、并发、持久化和审计记录。P0场景全部通过后，才能交付多人使用。

| 编号 | 操作场景 | 预期结果 |
| --- | --- | --- |
| AC01 | 学生报名时选择B校区，运营之后勾选并推送。 | 未推送时不进入校区招生队列；推送后仅B校区出现承接记录，来源与学生选择保留。 |
| AC02 | 运营查看已交接线索并尝试正价跟进。 | 能查承接和成功结果；正价跟进操作被拒绝。 |
| AC03 | A校区顾问直接访问B校区任务或导出数据。 | 详情、接口、搜索及导出均拒绝越权，不泄露记录。 |
| AC04 | 同一员工兼任A校区招生主管和B校区教师。 | 拥有两个独立岗位范围；不能管理B校区招生。 |
| AC05 | 同一活动重复报名；两个主管同时接收。 | 重复报名提示原记录；同一交接仅一个接收成功。 |
| AC06 | 应缴3,000元，先付500元，再付2,500元。 | 第一笔不计成功；第二笔后成功一次，保存缴清时间。 |
| AC07 | 重复提交凭证或再次保存已缴清订单。 | 不重复收款、不重复生成成交或续报业绩。 |
| AC08 | 教务负责两名教师的班级，另一班不归其服务。 | 仅访问所负责班级；能汇总两名教师班级，不能查看无关课程记录。 |
| AC09 | 两班分别18/20、24/30完成续报。 | 按本PRD建议粒度无重叠时，教务为42/50＝84%；机构不重复累计。 |
| AC10 | 教学主管调整续报期或处理期外续报。 | 按已配置规则执行；已有订单及历史成功不被静默改写。 |
| AC11 | 停用仍有任务和班级的员工。 | 提示交接清单；完成交接后新主责可处理、旧员工权限撤回。 |
| AC12 | 班级调换、任务改派、收款冲正后刷新和查看日志。 | 新状态持久保存；历史来源、金额变化和操作人可追溯。 |
| AC13 | 原营销入口提交；用户尝试进入旧页面操作。 | 迁移后使用统一对象和授权；未迁移入口明确限制，不能绕过新规则。 |

P1补充验收：转介绍的推荐关系全程保留；拓科与续报正确分类；明细合计与指标一致；退款与净成交按确认后的口径一致。

错误反馈应包含可执行的处理方式，例如“该员工不负责此校区，请重新选择接收人”；重复提交不得造成重复业务记录。

## 9 交付安排与待决策规则

### 交付基线和原型边界

Demo V2已演示活动交接、校区转化、岗位范围、班级服务、续报、分次收款、员工交接、拓科及转介绍。它采用浏览器本机数据和员工切换，尚不具备真实账号认证、服务端授权、真实支付或多人并发能力。旧营销入口也未自动进入新流程。

第一阶段完成P0业务闭环和本文件待决策规则。第二阶段完成指标下钻、转介绍拓科细节与旧入口迁移。正式上线前补齐服务端鉴权、事务及防重复处理、收款核销、退费对账、历史数据迁移和恢复能力。上述阶段不代表已承诺工期。

迁移时为员工建立稳定ID，映射班级教师与教务、线索来源与当前主责、历史订单及收款。缺失或冲突关系进入人工核对清单，不根据姓名或年级自动猜测归属。迁移后对账总订单、实收金额、未结任务和班级人数。
